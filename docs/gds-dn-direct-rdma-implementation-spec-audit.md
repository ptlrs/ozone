# Audit of `docs/gds-dn-direct-rdma-implementation-spec.md`

## Verdict
The spec is largely grounded in the current Ozone/HDDS codebase and in the checked-in cuObject API extracts, but it is not yet safe as a one-shot implementation plan. The biggest problems are scope leakage between Phase 1 and Phase 2, several Java 8 compile blockers, and a few semantic gaps in the RDMA GET path that would change existing S3 behavior.

## What Is Verified
- The baseline Ozone facts the spec relies on are correct: `DatanodeClientProtocol.proto` still ends `Type` at `ReadBlock = 24`, `DatanodeDetails.Port.Name` has no `RDMA` entry, `OzoneContainer` still wires `writeChannel` to Ratis and `readChannel` to gRPC, `HddsDispatcher` lives under `common/impl`, and `ObjectEndpoint.handleGetRequest()` still uses the current streaming/range behavior.
- The existing security/config surface is real: `hdds.block.token.enabled` and `hdds.grpc.tls.enabled` are already defined in `hadoop-hdds/common/src/main/resources/ozone-default.xml` and `hadoop-hdds/common/src/main/java/org/apache/hadoop/hdds/HddsConfigKeys.java`.
- The cuObject facts in the spec match the local NVIDIA extracts: `CUOBJ_GET` / `CUOBJ_PUT` exist, client-side memory registration is 4 GiB per call, server-side operations are 1 GiB per call, and scatter-gather registration tops out at 10 entries.
- The repo does not yet contain any RDMA-specific implementation artifacts. `container-service-native`, RDMA-specific protobufs, RDMA port plumbing, RDMA config keys, RDMA scripts, and RDMA test harnesses are all greenfield.

## Blocking Issues
- **Phase 1 and Phase 2 are mixed together.** The spec says Phase 1 is GET-only, but later sections still define `RdmaWriteBlock`, `rdmaReadFromRemote`, and other PUT-side code as if they were part of the implementation. That needs a hard boundary or an implementation agent will accidentally build Phase 2 pieces into Phase 1.
- **The spec uses Java syntax that does not compile under this repo's build.** The repo still compiles with `maven.compiler.release = 8`, but the spec uses `var` in multiple Java snippets and `java.util.zip.CRC32C` in the datanode checksum code. Both require newer Java levels than this project targets. The RDMA checksum path should reuse the existing Java 8-compatible checksum abstractions instead of the JDK 9+ class.
- **The native bootstrap snippet calls the wrong `NativeLibraryLoader` API.** `hadoop-hdds/rocks-native/src/main/java/org/apache/hadoop/hdds/utils/NativeLibraryLoader.java` only exposes `loadLibrary(String, List<String>)`, but the spec calls `NativeLibraryLoader.getInstance().loadLibrary(LIBRARY_NAME)`. That snippet will not compile unless the loader API changes or the call is rewritten.
- **The gateway RDMA filter handoff is coded against the wrong object.** `ObjectRequestContext` in `hadoop-ozone/s3gateway/src/main/java/org/apache/hadoop/ozone/s3/endpoint/ObjectEndpoint.java` does not expose `getProperty()`, so the spec's `context.getProperty(RdmaRequestFilter.RDMA_TOKEN_PROPERTY)` line is invalid. The endpoint needs to read from `getContext().getProperty(...)` or a helper on `S3RequestContext`.
- **The `maxConnections` knob is not mapped to a documented cuObjServer parameter.** The cuObjServer docs expose tunables like `num_dcis`, `cq_depth`, `max_sge`, and `delay_mode`, but not a `maxConnections` constructor argument. The spec needs to map this value to a real cuObjServer tunable or remove it.

## Semantic Gaps
- **The RDMA GET response does not preserve the normal GET response shape.** The current `ObjectEndpoint` path adds `Accept-Ranges`, quoted `ETag`, `Last-Modified`, tag count, custom metadata, and success metrics, and it distinguishes `200` vs `206` based on `rangeHeader.isReadFull()`. The RDMA branch in the spec only returns a raw `ETag` plus RDMA-specific headers and treats any non-null range as partial content. That will change S3 behavior unless the existing response helpers are reused.
- **The RDMA GET path does not state what to do about EC buckets or multipart part-number requests.** The normal GET path already has special handling for both, but the RDMA helper ignores them. The spec needs explicit fallback or support rules before any RDMA write starts.
- **Fallback after a partial RDMA transfer is unsafe.** The spec says to fall back to TCP if an RDMA request fails, but it does not prevent that fallback after some blocks have already been written into the client buffer. Once bytes have been transferred, a silent TCP retry can leave the buffer in a mixed or inconsistent state.
- **The datanode checksum path computes CRC32C but does not verify against stored checksum metadata.** The spec says the RDMA path should compute, verify, and return checksums, but the datanode snippet only computes a new CRC32C and returns it. It never compares the data against the existing block checksum metadata, and it hardcodes `checksumEnabled = true` even though the spec also defines `hdds.datanode.rdma.checksum.enabled`.
- **The datanode checksum size is wrong in the snippet.** `ChecksumData.Builder.setBytesPerChecksum(bufSize)` uses the RDMA buffer capacity, not the block's actual checksum granularity. That will produce misleading checksum metadata.
- **The gateway read path uses the wrong client-acquisition API.** Existing read flows in `hadoop-hdds/client/src/main/java/org/apache/hadoop/hdds/scm/storage/BlockInputStream.java` and `StreamBlockInputStream.java` use `acquireClientForReadData()` / `releaseClientForReadData()`. The spec's generic `acquireClient()` / `releaseClient()` path is not aligned with the current read semantics.
- **The `RpcClient.getKeyInfo` helper in the spec drifts from existing behavior.** `hadoop-ozone/client/src/main/java/org/apache/hadoop/ozone/client/rpc/RpcClient.java` already has a `getKeyInfo(volume, bucket, key, forceUpdateContainerCache)` overload that preserves `topologyAwareReadEnabled`, `latestVersionLocation`, and `forceUpdateContainerCacheFromSCM`. The spec's 3-argument helper hard-codes different behavior and should reuse the existing method instead of duplicating `OmKeyArgs` construction.
- **The block-range math is brittle.** The `blockStartGlobal` loop uses reference equality (`loc == locations.get(0)`) rather than index or block-ID comparison. That is a latent bug for range reads and filtered block lists.

## External Assumptions
- The environment and cloud-provider sections are external to the Ozone repo and should stay treated as vendor facts, not code facts. I spot-checked the Crusoe pricing claims against the public pricing page and they are plausible, but Lambda/Vultr networking claims and instance availability still need independent verification before procurement.
- The spec already marks `SoftRoCE` / DC transport support as uncertain. That is the right stance to keep until hardware testing proves otherwise.

## Bottom Line
The spec is a solid design draft, but it is not yet a safe one-shot implementation target. Fix the phase-scope split, the Java 8 compile blockers, the gateway context/header parity, and the checksum/fallback semantics before handing it to an implementation agent.
