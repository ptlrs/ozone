## Overview

`container-common` supplies the shared data types, DTOs, exception hierarchy, and configuration that SCM's ContainerManager, ReplicationManager, and ContainerBalancer use. `ContainerInfo` is the central DTO carrying ContainerID, state, ReplicationConfig, pipeline ID, and size; it round-trips through Protobuf via `toProto()` / `fromProtobuf()`. `ContainerID` is a value-typed long wrapper with a RocksDB `Codec` backed by `LongCodec`. `ContainerBalancerConfiguration` is the `@ConfigGroup(prefix = "hdds.container.balancer")` POJO with 15+ parameters and a `validate()` method that enforces that `maxSizeEnteringTarget` and `maxSizeLeavingSource` are not smaller than the configured container size. `ReplicationManagerReport` accumulates per-state container counts and is the primary reporting object emitted after each ReplicationManager scan cycle. Supporting the hierarchy are seven exception classes covering missing containers, invalid states, uncommitted blocks, and SCM-level storage errors; and helper classes such as `ExcludeList`, `AllocatedBlock`, `ContainerWithPipeline`, and `MoveDataNodePair` used in block allocation and container move paths.

## Sharp edges

- `ContainerInfo.fromProtobuf()` previously created two `ContainerInfo` instances per deserialization call ([HDDS-14196](https://issues.apache.org/jira/browse/HDDS-14196)); the second instance was discarded but this caused measurable GC pressure in high-throughput SCM paths. Fixed by collapsing to a single construction path in `fromProtobuf()`.
- `ContainerBalancerConfiguration.validate()` was not called at startup before [HDDS-15535](https://issues.apache.org/jira/browse/HDDS-15535); invalid configurations (e.g., `maxSizeEnteringTarget` smaller than container size) silently produced incorrect balancer behavior rather than a startup failure.
- `ExcludeList` is thread-safe at the field level but the combination of `addContainerID` and `getContainerIds` is not atomic; callers in the block allocation path must ensure they hold the relevant lock around the check-then-act sequence.

## Self-quiz

1. `ContainerInfo` carries a `LifeCycleState`. List all valid states in order of the normal container lifecycle from creation to deletion, and name the class in this feature that represents each abnormal health assessment.
2. What two constraints does `ContainerBalancerConfiguration.validate()` enforce, and what happens if either is violated after [HDDS-15535](https://issues.apache.org/jira/browse/HDDS-15535)?
3. `ContainerID` uses `LongCodec` as its RocksDB codec. What is the benefit of using a primitive codec rather than a Protobuf codec for a simple long value?
4. `ExcludeList` is listed as `thread-safe`. Describe a scenario where a caller could still observe a race condition when using `ExcludeList` in block allocation.
5. `ContainerChecksums` was introduced by [HDDS-13305](https://issues.apache.org/jira/browse/HDDS-13305). What problem does wrapping checksum data in a separate object solve compared to storing raw bytes directly on `ContainerInfo`?

<details>
<summary>Answers</summary>

Answer 1: Normal lifecycle: OPEN → CLOSING → QUASI_CLOSED → CLOSED → DELETING → DELETED. Abnormal health is represented by `ContainerHealthState` (the enum) which maps to states like UNDER_REPLICATED, OVER_REPLICATED, MIS_REPLICATED, EMPTY, UNHEALTHY.
Answer 2: `validate()` checks (1) `maxSizeEnteringTarget >= containerSize` threshold and (2) `maxSizeLeavingSource >= containerSize` threshold; after [HDDS-15535](https://issues.apache.org/jira/browse/HDDS-15535) a violation throws `IllegalArgumentException` at ContainerBalancer startup rather than silently proceeding.
Answer 3: `LongCodec` serialises as 8 bytes using direct `ByteBuffer.putLong()`; a Protobuf codec adds varint framing overhead and object allocation on every encode/decode, which matters at SCM scale with millions of container ID lookups.
Answer 4: A caller that calls `excludeList.getContainerIds()` and then checks whether a container is present may observe a stale snapshot if another thread calls `addContainerID()` between the get and the check; the individual operations are atomic but the check-then-act pattern is not.
Answer 5: Separating checksum data into `ContainerChecksums` avoids bloating `ContainerInfo` with variable-length byte arrays that are only needed during verification; it also allows checksum data to be loaded lazily from a separate RocksDB key rather than on every `ContainerInfo` read.

</details>
