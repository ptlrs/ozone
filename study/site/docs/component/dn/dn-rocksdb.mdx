## Overview

The `dn-rocksdb` feature group defines the RocksDB-backed metadata stores used by datanode containers. There are three schema versions reflecting the evolution from a single default column family (schema v1) to per-container RocksDB instances with three column families (schema v3). `AbstractDatanodeStore` is the common base that opens the RocksDB file, exposes named `Table` handles for `blockData`, `metadata`, `deletedBlocks`, and `finalizeBlocks` column families, and implements `DatanodeStore` and `DBStoreManager`. `DatanodeStoreSchemaOneImpl`, `DatanodeStoreSchemaTwoImpl`, and `DatanodeStoreSchemaThreeImpl` are the three concrete versions; schema v3 ([HDDS-6597](https://issues.apache.org/jira/browse/HDDS-6597)) places each container in its own RocksDB under a `DbVolume`, enabling per-volume RocksDB consolidation. `WitnessedContainerMetadataStoreImpl` is a special single-database on the "master volume" that tracks container IDs created on this datanode — its `containerIds` table stores `ContainerID → ContainerCreateInfo` (value changed from string to proto in [HDDS-13176](https://issues.apache.org/jira/browse/HDDS-13176)). `AbstractRDBStore` is the generic base for all RocksDB stores on the datanode, implementing batched writes and iterator management.

## Sharp edges

- `AbstractDatanodeStore.close()` must only be called by `ReferenceCountedDB`; direct `close()` while another thread holds the DB handle causes a use-after-free on the RocksDB native iterator (HDDS-14800 partially mitigated by guarding the iterator, but the root contract must still be respected).
- Schema v1 stored block IDs as raw `long` keys; `SchemaOneKeyCodec` and `SchemaOneDeletedBlocksTable` exist solely to read these legacy instances during upgrade finalization and must not be used for new writes.

## Self-quiz

1. Schema v3 places multiple containers' block data into a single per-disk RocksDB using a container ID prefix on block keys. What is the key prefix format, and which codec enforces fixed-length encoding?
2. `WitnessedContainerMetadataStoreImpl` is stored on the "master volume". What is the master volume, and what happens if it is lost?
3. `SchemaOneKeyCodec` exists to decode legacy schema v1 keys. After finalization to schema v3, can schema v1 containers still exist on a datanode, and if so, what happens when `BlockManagerImpl` tries to read them?
4. `AbstractRDBStore.initDBStore` takes a `ManagedDBOptions` argument. What happens if two `AbstractDatanodeStore` instances are opened for the same RocksDB path concurrently?
5. `ContainerCreateInfo` stores `ContainerCreateInfo` (proto). What fields does it contain, and when is it written vs. read?

<details>
<summary>Answers</summary>

Answer 1: The key is a `FixedLengthStringCodec`-encoded container ID concatenated with the block ID; fixed-length encoding prevents a 10-digit container ID from being treated as a prefix of a shorter one during range scans.
Answer 2: The master volume is the first `DbVolume` in the configuration; the `containerIds` table records all containers ever created on this datanode. If it is lost, SCM must rely on full container reports to re-discover the datanode's containers.
Answer 3: Yes, schema v1 containers remain on disk until finalization runs; `BlockManagerImpl` detects schema v1 by checking `KeyValueContainerData.getSchemaVersion()` and uses `SchemaOneKeyCodec` to decode keys.
Answer 4: RocksDB will fail to open the second instance with a "lock file already held" error; the caller should use `ContainerCache`/`DatanodeStoreCache` to ensure at most one open handle per path.
Answer 5: `ContainerCreateInfo` contains container state and creation timestamp; it is written when a container is created (`WitnessedContainerMetadataStoreImpl.addContainer`) and read on restart to rebuild the in-memory container set.
